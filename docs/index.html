Why the all-time rate looks so high — and what to trust instead

Short answer: exclude untagged bugs and measure recent months separately. Excluding untagged bugs alone isn't enough — the old backlog is so sparsely tagged that what's left over is still a small, skewed sample.

What's actually happening "Issued by" tagging discipline has changed sharply over time. In July, only 57 of 158 bugs (36%) had the field set at all — too little and too skewed toward Support (who gets auto-tagged via the support intake process) to trust. By August that jumped to 82% tagged. Since September 1, it's 100% — every single new bug has Issued by set. The all-time 74.3% figure blends all of that together, so it mostly reflects old data-entry gaps, not current quality.
Escape rate by month, moved to the Overview tab The month-by-month chart now lives on the Overview tab, right under the portfolio headline — along with a date-range picker (this month / a specific month / this year / last year / all time) on the headline escape-rate KPI itself, so you're not stuck with a fixed window.
Recommendation Use trailing-month escape rate (currently 42.2%, from September) as the default view, not the all-time figure — that's the Overview tab's default. Once 2–3 more fully-tagged months land, a rolling 3-month average will be more stable than any single month. The all-time and customizable views below are still useful for historical/audit purposes, just not as the primary KPI.

Hardware-related bugs opened by Support — per device

Every FW bug with Issued by = Support, grouped purely by hardware device. This is the full Support backlog across all firmware versions combined — not scoped or filtered by version, so it reflects which physical devices customers report problems on most, independent of which firmware they were running.

Note on the HW project Shelly's Jira also has a separate HW — "Hardware Team" project. It does not track defects the way FW/FE do: of its 263 items, 217 are "Task" and 2 are "Story" — zero use the "Bug" issue type, and the "Issued by" field (the backbone of every escape-rate number on this page) has never been set on any of them. It's used as a hardware board/module engineering backlog (e.g. "Shelly ESP32 C5 Vert Module...", "Requirements file for BK7239N"), not a bug tracker. Its current status split: 157 Done, 52 In Progress, 54 To Do. Because it has no defect data, hardware-related bug statistics come from FW instead (below), where Support-reported issues are tagged with a Device field — that's what this section shows.

What each metric measures

Issued by

Required select field on every FW/FE Bug. Support = a customer hit it (escaped to prod). QA / QA Automation / PO / Development / Integrations / Front End / Back End / Documentation = caught internally before release. This is the backbone of every "escape rate" number on this dashboard.

Firmware Version

customfield_13320. As of this rebuild it's a clean multiselect of predefined version strings (no more free text). An issue can carry more than one version if it was verified as reproducing across a regression window — that issue is then counted once per version it's tagged with.

Shelly Component

customfield_13319. Subsystem/protocol tag (Zigbee, MQTT, Matter, HTTP, Schedule, etc). Used for the Component filters on the Version Explorer and Devices tabs. Distinct from the "Feature" field, which is not currently surfaced here.
Field migration note The Firmware Version field used to be free text (customfield_13220) with inconsistent formats and unreliable JQL text search — a version like "2.0.1" would sometimes return 0 results despite being visibly present on issues. That field has been superseded by a clean predefined-values field (customfield_13320), which this entire dashboard is now built on. The old field is no longer used here; its historical data isn't included since it can't be reliably reconciled with the new one.
Coverage 28 of 522 FW bugs currently carry a Firmware Version tag — this field is still being adopted retroactively, so version-scoped numbers above cover a growing subset, not the full backlog. All portfolio-level totals (headline KPIs, Issued-by pies, escape rate) use the full 522/696 bug counts regardless of version tagging.

Live data settings

Connect your own Jira account to refresh every number on this page with data as of right now, instead of the last weekly snapshot. Your token stays in this browser only — it's saved to this device's local storage and sent, with each request, straight to the read-only relay below. It is never sent anywhere else and never leaves this browser except to that relay.

Where do I get a token? id.atlassian.com → Security → API tokens → Create token, using the Jira account you want the dashboard to query as.

What's the relay URL? Browsers can't call Jira's API directly (Jira blocks cross-site requests), so a small read-only relay forwards your request and adds your own token — it never stores it. See the repo README for a one-click relay you can deploy under your own account. Without a relay URL, this page stays on the weekly snapshot.
